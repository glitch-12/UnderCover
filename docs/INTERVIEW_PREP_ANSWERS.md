# Interview Prep — Answer Key

## 1. High-Level System Design & Product Architecture

**1. Why split `core/` vs `games/undercover/`?**
`core/` holds anything that's true regardless of which party game is being played: a player roster (`RoomEngine`), a generic phase state machine (`TurnEngine`), and content delivery with anti-repeat logic (`ContentEngine`). `games/undercover/` holds only what's specific to *this* game: role-assignment math, win-condition rules, and the screens. The payoff is that a second title reuses the room/turn/content machinery untouched and only writes its own `logic/` + `screens/` — you're not forking a whole app per game.

**2. Cost of the `GameModule` interface pattern from day one?**
You pay upfront: an extra layer of indirection, a contract you have to design correctly before you have a second consumer to validate it against, and the temptation to over-generalize `TurnEngine`'s phases for a game that doesn't exist yet. It's worth it here because the product vision is explicitly a platform (§1), and the *shape* of a second title ("Guess the Person") is already sketched with the same room/content/turn primitives (§2.3) — so the abstraction is validated by a real second use case, not speculative. If there were no credible second game, this would be premature abstraction; build single-purpose and extract the interface later once a second consumer actually exists.

**3. Do you need a backend?**
No, not for the MVP loop — role assignment, turns, and voting are all local, single-device state (`RoomEngine`/`TurnEngine` are pure Zustand stores, no network). The first real backend need is a **content-delivery API** (§6.3), because the actual complaint driving the doc ("words feel repetitive") has two causes: a small bundled pool and, more fixably, naive randomness — fixed client-side by the deck/shuffle model (§6.2) — and, separately, a genuinely small pool that only a server-delivered, versioned pack update can grow without an app-store release. Realtime multiplayer is deferred (Phase 2) because it's a much bigger investment (room/session server, reconnection handling) that isn't needed to fix the thing users are actually complaining about.

**4. Online multiplayer design + hardest part?**
The existing `TurnEngine` is already a pure phase-transition reducer keyed off explicit actions (`startVote`, `eliminatePlayer`, …) with no rendering or IO baked in — that's exactly the shape you want to run inside a realtime room server (e.g. Colyseus, per §7) and broadcast state diffs from. Each client becomes a thin renderer of `RoundState` instead of the source of truth. The hardest part is reconnection: a player backgrounding mid-vote and coming back needs to resync to the *current* phase without re-triggering side effects (re-showing a role reveal, double-counting a vote) — state needs to be idempotent to re-delivery, which the current single-device design never had to consider.

**5. Why an explicit phase enum over booleans?**
With 9 phases, a boolean-per-phase scheme (`isVoting`, `isEliminating`, …) allows invalid combinations by construction — e.g. `isVoting && isEliminating` both true is meaningless but the type system can't stop it, and every reducer would need to manually maintain mutual exclusion. A single `phase: RoundPhase` string union makes invalid states unrepresentable and turns "what can happen next" into a switch/guard per action (see `wrongPhase()` in `TurnEngine.ts`) instead of an ad hoc web of flag checks.

**6. How do variants avoid new screens?**
`assignRoles(players, variant, wordPair)` takes an `UndercoverVariantConfig` (`mrWhiteEnabled: boolean`, `undercoverCount: (playerCount) => number`) and produces the same `RoleAssignment[]` shape regardless of variant — screens only ever render `RoleAssignment`/`RoundState`, never variant-specific fields. All three variants differ purely in the *data* fed into one function, not in control flow the UI has to branch on.

**7. Plan to fix "words feel repetitive"?**
Two independent fixes, and it matters that they're independent: (a) client-side, replace naive random draw with the deck model (`deck.ts`) — shuffle once, draw without replacement, exclude recently-drawn ids from the front of a reshuffle — which fixes the *feel* of repetition even with the same word count; (b) server-side, move packs behind a versioned content API so new words ship without an app release, with a bundled seed pack (`src/packs/`) so day-one/offline users are never blocked on network. Trade-off: a bigger local bundle is simpler (no backend, no cache invalidation) but caps content growth at binary-release cadence; a remote API adds real infrastructure (auth-free is fine for read-only packs, but you still need versioning, caching, ETag/offline handling) in exchange for being able to add words without shipping.

**8. Adding "Guess the Person" tomorrow?**
Touch: a new `src/games/guess-the-person/` folder (config, logic, screens) and one registry entry in `src/app/gameRegistry.ts`. Don't touch: `RoomEngine`, `ContentEngine`, `TurnEngine`, navigation shell, or theming — all game-agnostic by design. You would extend `TurnEngine`'s phase set if the new game's loop doesn't map onto the existing phases (ask/answer instead of clue/vote), which is the one place the "generic" core might leak game-specific assumptions and need a second look.

## 2. Mid-Level — Mobile / React Native Engineering

**9. Why Zustand over Redux/Context?**
No boilerplate (no actions/reducers/dispatch ceremony, no Provider tree) for what's fundamentally a couple of small state machines. `create<RoomStore>((set, get) => ({...}))` reads like a plain object with methods; Redux would add indirection (action creators, a reducer switch) for the same logic with no real payoff at this scale, and Context alone doesn't give you the outside-React `get()` access the stores use for validation (e.g. `get().players.length >= maxPlayers` inside `addPlayer`).

**10. Why MMKV over AsyncStorage?**
MMKV is synchronous and much faster (backed by native key-value storage, no bridge round-trip per call), which matters here because `ContentEngine` persists the deck cursor on every single `drawPair()` call — doing that async would add latency/complexity for no benefit, since the write is small and frequent.

**11. Why two stores instead of one?**
`RoomEngine` (who's in the game) and `TurnEngine` (what phase the game is in) have different lifecycles — the room persists across "play again," but round state resets every game (see `playAgain()` resetting to `createInitialRoundState()` while players stay untouched). Splitting them means each store's phase-guard logic only has to reason about its own concerns, and a future second game module can reuse `RoomEngine` while bringing its own turn logic if needed.

**12. Why `{success, error}` instead of throwing?**
These are *expected*, user-facing failure paths (name too long, wrong phase, index out of bounds) — not exceptional program states. Returning a result object forces the call site (a screen) to explicitly handle failure (e.g. show the error inline) rather than needing a try/catch around every store call, and it keeps these pure functions easy to unit test (assert on the return value, no exception-matching).

**13. Adding a third theme?**
`useTheme()` currently branches on `useColorScheme()` between `darkColors`/`lightColors`. A third theme (e.g. high-contrast) would extend that branch to read a user preference (persisted via MMKV) instead of purely the OS setting, and as long as the new palette satisfies the same `ThemeColors` shape, every screen that destructures `colors.X` needs zero changes — the whole point of the token system (`colors.primary`, `colors.surface`, …) is that screens never hardcode hex values.

**14. `npm run android` to pixels?**
Metro bundles the JS (transforms TS/JSX, resolves the module graph) and serves it over a dev socket; in parallel Gradle builds the native Android shell (compiles Kotlin/Java native modules — including any autolinked ones like gesture-handler, reanimated, mmkv's native bindings — and links them into the APK) and installs it on the device/emulator; on launch the native shell boots a JS engine (Hermes) that fetches the bundle from Metro (`Loading from 10.0.2.2:8081…`, which you'd have actually seen this session), executes it, and React Native's bridge/fabric renders the component tree to native views.

**15. The AdMob Kotlin metadata error — root cause?**
Kotlin classes carry a compiled *metadata version* (separate from the language version) describing the compiler that produced them. `play-services-ads` (Google's prebuilt AAR) was compiled by a Kotlin 2.3.0 toolchain; this project's Kotlin Gradle plugin was pinned at 2.1.20, whose compiler can only *read* metadata up to a lower ceiling — so it can't parse the dependency's compiled classes at all, and compilation of any module that touches it (including transitively, like gesture-handler once you start bumping versions) fails. Fixes, in order of invasiveness: (a) bump your project's Kotlin to match or exceed 2.3.0 — tried this, it cascaded into new failures in unrelated native modules (`react-native-safe-area-context`, `react-native-gesture-handler`) because bumping one Gradle-level `ext.kotlinVersion` doesn't uniformly re-resolve every module's own Kotlin plugin version; (b) pin the dependency to an older release compiled against 2.1.x — viable but fragile long-term; (c) drop the dependency — what actually happened here, per explicit instruction, since ads weren't load-bearing for the task at hand.

**16. Manifest merge conflicts / `tools:replace`?**
Android merges the app's `AndroidManifest.xml` with every library's own manifest at build time. Two `<meta-data>` elements with the same `android:name` but different `android:value` (the app's real AdMob App ID vs. the SDK's own placeholder/default entry) is treated as an unresolved conflict, so the build refuses to guess which one wins — `processDebugMainManifest` fails loudly instead of silently picking one. `tools:replace="android:value"` tells the merger "the app manifest's value wins, don't complain"; `tools:remove` would instead delete the library's element entirely. You'd reach for fixing the source dependency instead of either `tools:` attribute when the conflict signals an actual incompatibility (e.g. a library manifest requiring a permission or SDK version your app explicitly wants to exclude) rather than a legitimate "app overrides library default" case like this one.

**17. Ruby 4.0 / CocoaPods breakage?**
Two separate failures, same root cause (toolchain drift): `String#untaint` was removed in modern Ruby (a no-op safety API from Ruby's old taint-checking model), so the project's pinned Bundler 1.17.2 — old enough to still call it — crashes immediately on this Ruby. Routing around `bundle exec` and calling the Homebrew-installed system `pod` directly (`pod install`) sidesteps the *Bundler* incompatibility, but then hit a second, unrelated issue: CocoaPods' own error-reporting path called `String#unicode_normalize` on a binary (`ASCII-8BIT`) string, which only throws under certain locale/encoding configurations — fixed by explicitly setting `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8`. Both are workarounds, not fixes: the real fix is updating the pinned `Gemfile.lock`/Bundler version (and possibly the Ruby version pin) so the project's own tooling works without hand-tuned environment variables — worth flagging as follow-up debt even though it unblocked the immediate task.

**18. i18n — what's actually wired vs. what's needed for a 2nd locale?**
`react-i18next` is initialized and `src/i18n/en.json` exists as a translation resource, and screens like `RoleReveal`/`ClueTurn`/`Vote` already pull strings through `t()` — that part is real. What's *not* there: a second locale file to switch to, any locale-selection UI/persistence, and — the actual inconsistency — `Home.tsx` has hardcoded literal strings (`"Party Game Hub"`, `"Pick a game to start playing"`) never routed through `t()` at all, plus the word pack itself is locale-locked by filename (`seed-en.json`, with a `locale: "en"` field already in the schema) with no second pack to switch to. So "i18n-ready" is true for the game *screens* but not yet true for the Home hub or the content layer.

## 3. Low-Level — Code Reading & Algorithms

**19. Why is `shuffle()` (Fisher–Yates) correct?**
It walks from the last index down to 1, swapping each element with a uniformly random element at or before its current position (`j = Math.floor(rng() * (i + 1))`), so every element has an equal, independent chance of ending at every final position — a mathematically uniform permutation. `.sort(() => Math.random() - 0.5)` is biased because comparison-sort algorithms assume a *consistent* comparator; feeding it a random one violates that assumption, and depending on the engine's sort implementation (which is not guaranteed to be a full pairwise comparison — V8's `Array.sort` is Timsort-based), certain permutations become measurably more likely than others. It's not just "slower," it's mathematically not a fair shuffle.

**20. `reshuffle()` — what and why?**
It splits `allIds` into `fresh` (not in `recentHistory`) and `recent` (in `recentHistory`), shuffles each independently, and returns `[...shuffle(fresh), ...shuffle(recent)]` — recent ids are still included (nothing is permanently excluded) but forced to the *back* of the new draw order. `recentHistorySize` bounds how many of the most-recently-drawn ids get this "not too soon" protection — the larger it is, the longer a pair stays out of the front of the deck after being drawn, at the cost of needing a bigger pool of "fresh" ids to draw from meanwhile. If `recentHistorySize >= allIds.length`, `fresh` becomes empty on every reshuffle (everything is "recent"), degenerating to just `shuffle(allIds)` — no real protection left, though also no crash.

**21. Trace: 5-pair deck, `recentHistorySize=1`, 6 draws.**
Calls 1–5 drain the initial shuffled `order` sequentially (cursor 0→5), and after call 5 `recentHistory = [<pair drawn on call 5>]` (history size 1, so only the single latest draw is kept). Call 6: `cursor(5) >= order.length(5)`, so `reshuffle()` runs — it puts the call-5 pair into `recent` and every other pair into `fresh`, returning `shuffle(fresh) + shuffle(recent)`. The new `order[0]` (what call 6 actually draws) is drawn from `fresh`, so **the pair drawn on call 5 cannot be drawn on call 6** — it's guaranteed to land last in the new order, not first.

**22. Why check `packId` *and* `packVersion`?**
`packVersion` bumping signals the pack's *contents* changed (pairs added/removed/edited) — a persisted `order`/`cursor` from before the bump refers to a pair set that may no longer match reality, so trusting it could skip newly-added pairs entirely (they'd never be in `order`) or point `cursor` at a now-meaningless position. Rejecting the whole persisted deck on a version mismatch is simpler and safer than trying to merge new ids into an in-progress shuffle: `createDeck()` from scratch guarantees correctness, whereas patching risks either duplicate draws or permanently-unreachable new pairs. The `order.length !== allIds.length` check after filtering is the same idea for a second failure mode — if the pack quietly changed shape without a version bump (or historical data drifted), don't trust a partial/malformed order either; same escape hatch, don't patch.

**23. `resolveUndercoverCount`'s double clamp — what does each side defend?**
`Math.max(1, variant.undercoverCount(playerCount))` guards the *lower* bound — without it, a variant formula like Multi-Undercover's `floor(playerCount/4)` returns `0` for small tables (e.g. 3 players), which would produce a game with zero Undercover players (no game). `Math.min(..., maxUndercover)` guards the *upper* bound — without it, a variant formula could return a number that leaves fewer than 1 Civilian standing (e.g. requesting `undercoverCount = playerCount - mrWhiteCount`, which would mean everyone is an impostor and nobody plays "civilian" at all) — `maxUndercover = playerCount - mrWhiteCount - 1` always reserves at least one Civilian slot.

**24. `playerCount=3`, Multi-Undercover → still 1 Undercover, not 0.**
`mrWhiteCount = 0` (Multi-Undercover has `mrWhiteEnabled: false`). `maxUndercover = max(0, 3 - 0 - 1) = 2`. `variant.undercoverCount(3) = floor(3/4) = 0`. `Math.max(1, 0) = 1`. `Math.min(1, 2) = 1`. The inner `Math.max(1, …)` floor is what saves this — it overrides the variant's raw formula output whenever that formula would leave zero Undercover players, as long as the upper clamp still permits at least 1 (it does here, since `maxUndercover = 2 ≥ 1`).

**25. Why shuffle the roles array instead of the players array?**
Both are correct ways to get a random assignment, but shuffling `roles` (a short, fixed-composition array like `['undercover', 'civilian', 'civilian', 'civilian']`) and then zip-mapping by index onto `players` in their existing order is simpler to reason about: you build the *exact* multiset of roles once (`undercoverCount` copies of `'undercover'`, `mrWhiteCount` copies of `'mrWhite'`, the rest `'civilian'`), and one shuffle distributes them. Shuffling players first and then assigning "first N get Undercover" would require you to *also* separately track which shuffled-player-index maps to which original player identity — strictly more bookkeeping for the same outcome, since player identity never needs to be reordered, only role labels do.

**26. Why `>=` not `>` in `checkWinner`? 2-player endgame?**
With `1` Undercover and `1` Civilian left, `undercoverCount(1) >= civilianCount(1)` is true → Undercover wins, matching the architecture doc's stated rule verbatim ("Undercover count ≥ remaining Civilians"). The intuition: once the Undercover is no longer *outnumbered*, they can't realistically be voted out by a Civilian-majority anymore — a 1v1 is already unwinnable for the Civilians going forward, so the game correctly ends there instead of forcing one more pointless vote. If it were `>` instead, a 1-vs-1 would return `null` (no winner) and the state machine would loop back into another `clueTurn` round with two players who can never resolve the vote (any elimination just flips who's "left"), risking a game that never naturally terminates.

**27. `checkWinner` with Mr. White alive and Undercover count 0 — reachable, and correct?**
Yes, reachable: in the Mr. White variant (`undercoverCount() => 1`, `mrWhiteEnabled: true`), if the single Undercover is voted out in an earlier round while Mr. White survives, a later `checkWinner(remainingRoles)` call has `undercoverCount = 0` but `mrWhiteCount = 1`. The civilians-win branch requires *both* `undercoverCount === 0 && mrWhiteCount === 0`, so this correctly returns `null` (game continues) rather than declaring Civilians the winner — matching the product rule that Civilians must eliminate **all** impostors, Undercover *and* Mr. White, not just the "official" Undercover. This is a good example of a subtle-but-intentional AND condition that's easy to misread as redundant if you only think about the single-variant (Classic, no Mr. White) case.

**28. Where does vote tallying actually live, and why not in `TurnEngine`?**
Not in these files — `TurnEngine.eliminatePlayer(playerId)` takes the *result* of tallying as an already-decided input; tally/majority logic lives in the `Vote` screen (per the screenshots this session, it renders live vote counts and a tie-revote prompt — `"It's a tie between {{names}} — revote!"` in `src/i18n/en.json`). Keeping it out of `TurnEngine` keeps the state machine's job purely "what phase are we in and what transitions are legal," independent of *how* a phase's outcome gets decided — a future variant with different voting rules (ranked choice, no-elimination bluff rounds) only changes the screen, not the engine.

**29. Is recomputing `activePlayerOrder` every call a real perf concern?**
No — `turnOrder` caps at 20 (`UNDERCOVER_MAX_PLAYERS`), so filtering it against a `Set` built from `eliminatedPlayerIds` is O(20) at worst, called a handful of times per round, not per frame. Caching it would only pay off at a scale this app will never hit, and would introduce a real correctness risk instead: the cache would need perfect invalidation exactly whenever `eliminatedPlayerIds` changes (which is the same event that already triggers the recompute today), so you'd be trading "always correct, technically redundant work" for "same amount of logic, plus a new way to go stale." Classic case of premature optimization.

**30. Phase guards — benefit and cost?**
Benefit: they make illegal transitions impossible to execute silently — e.g. a stale UI callback firing `eliminatePlayer` after the phase already moved to `discussion` (a double-tap, a race between two rapid taps, a screen that didn't unmount its handler) is rejected with a clear `{success:false, error}` instead of corrupting `RoundState` (e.g. appending to `eliminatedPlayerIds` while the round hasn't even reached `vote` yet). Cost: it's the same `if (state.phase !== 'X') return wrongPhase(...)` boilerplate repeated in every action, and there's no compiler enforcement that a *new* action added later remembers to include it — forgetting the guard silently reopens the exact class of bug the pattern exists to prevent. At this action count (9) it's a reasonable manual pattern; past a much larger phase count you'd want a table-driven transition map that makes "forgetting a guard" structurally impossible.

**31. Is missing duplicate-name/max-length validation in `addPlayer` a real gap?**
Arguably yes for duplicate names specifically — two players named "Alex" would both render identically on `RoleReveal`/`Vote` screens ("Alex, vote to eliminate: ... Alex"), which is a real UX confusion the current empty-string-only check doesn't catch. Max length is a smaller concern (mostly a layout/overflow issue, not a correctness one). The right layer is `RoomEngine.addPlayer` itself, not the screen — it already owns the "is this name valid" decision (the empty-check is exactly this kind of validation) and returns `{success:false, error}` in a shape the `Lobby` screen is already built to surface, so extending it is consistent with the existing pattern rather than duplicating validation in the UI.

**32. `generatePlayerId()`'s module-level counter — does it actually bite?**
In principle, a module-level counter is fragile: if the module gets re-evaluated (a fresh `require`/import in an isolated Jest module registry, or in some Fast Refresh edge cases where React Native resets module state without a full reload) the counter resets to 0, and IDs like `player-1` could collide with previously-generated (and still-referenced-elsewhere) ids. In practice here it's low-risk: within a single app session the module is only ever loaded once, ids only need to be unique for the lifetime of one `RoomStore` (never persisted or compared across app restarts), and the Jest test suite (per the actual test file) constructs fresh players per test without asserting on specific id *values* — so nothing currently depends on global uniqueness across reloads. It's a reasonable simplification for the current scope, but the honest answer in an interview is "this would need to become a UUID the moment ids need to survive a reload or be compared across sessions" — showing you know *why* it's currently safe rather than just "it's fine."

## 4. Testing

**33. Why almost all pure-logic tests, and what's not covered?**
Nearly everything with real branching logic here (`RoomEngine`, `TurnEngine`, `ContentEngine`, `deck`, `assignRoles`, `winCondition`) is a plain function or a Zustand store with no rendering — so unit-testing it is cheap, fast, and doesn't need a rendering environment at all. It's also where the actual risk lives: a wrong phase transition or a broken shuffle is a game-breaking bug, whereas a screen rendering the wrong padding is a visual nit you'd catch by eye. What's *not* covered by this suite: whether a screen actually calls the right store action on the right button tap, whether text is correctly localized/rendered, layout/overflow at extreme name lengths or 20-player lists, and anything only visible by actually running the app — which is exactly why this session's Play Store screenshots were captured by driving a real emulator rather than trusted to component tests.

**34. Why injectable `rng`/`store`, and a deterministic shuffle test?**
Both `Math.random` and the real MMKV instance are non-deterministic/impure dependencies that would make tests flaky or require mocking a native module. Accepting them as optional parameters with real defaults means production code needs zero changes while tests can inject a seeded/fake version. A deterministic test: pass a counting or fixed-sequence `rng` (e.g. one that always returns the same sequence of values) into `shuffle([1,2,3,4,5], fakeRng)` and assert the exact resulting order — or, for a fairness check without full determinism, run `shuffle` thousands of times with real `Math.random`, tally how often each element lands in each position, and assert the distribution is roughly uniform (within a statistical tolerance) rather than skewed toward any position.

**35. Testing `resolveUndercoverCount` never returns 0 across all variants/player counts?**
Exhaustive loop, not property-based, because the input space is small and fully enumerable: 3 variants × player counts 3–20 is 54 cases — well within "just loop and assert" territory. Property-based testing earns its complexity when the input space is large/continuous or the property is easier to state than to enumerate over; here `for (const variant of undercoverVariants) for (let n = 3; n <= 20; n++) expect(resolveUndercoverCount(n, variant)).toBeGreaterThanOrEqual(1)` is more readable and exactly as rigorous.

**36. Real-emulator screenshots vs. component tests?**
Driving `adb`/`uiautomator` against a booted emulator catches things no component test can: real native rendering (fonts, actual pixel layout, status bar overlap), real navigation transitions, and — concretely, this actually happened mid-session — button coordinates shifting because player-count text changed the layout above it, which a snapshot test wouldn't have caught either (snapshots compare serialized trees, not visual pixel positions). The cost is exactly that fragility: hardcoded tap coordinates broke repeatedly during this session whenever the screen state didn't match assumptions, which is why later steps switched to reading `uiautomator` bounds dynamically instead of eyeballing scaled screenshots — a real instance of "brittle E2E automation" that's worth being able to discuss honestly rather than pretend it went smoothly.

## 5. Behavioral / Project Narrative — talking-point outlines

**37. Pre-existing bug found mid-task (`Home.tsx` unclosed brace).**
Situation: doing unrelated store-asset work, ran `tsc --noEmit` as a sanity check before an Android build and hit a syntax error nowhere near anything just touched. Task: decide whether fixing it was in scope. Action: verified it predated the session's changes (checked git blame/diff), confirmed it was a genuine blocker (the app couldn't type-check, and — separately — the file wouldn't reliably bundle), and fixed the minimal one-line issue rather than expanding scope. Result: unblocked the actual task (needed a working build to take screenshots) without turning a "generate store assets" request into an unrelated refactor. The generalizable point: fix pre-existing bugs you *trip over* and that block your actual goal; don't go looking for more once the blocker's cleared.

**38. Dependency conflict you couldn't cleanly resolve.**
Situation: Android build failing on a Kotlin metadata version mismatch from `react-native-google-mobile-ads`. Task: get a working build. Action: tried the "proper" fix first (bump the project's Kotlin version) — it made things *worse* (cascaded into two more modules failing) rather than better, which was the signal to stop pulling that thread. Reverted the version bump back to a known-good state immediately rather than trying to also patch the newly-broken modules. Then, since the user explicitly said to drop AdMob if it was causing problems, removed the dependency entirely across every platform surface (JS, Android manifest, iOS Info.plist/Podfile) rather than leaving it half-removed. Result: both platforms build clean, tests still pass. The generalizable point: know the difference between "this fix needs one more small push" and "this fix just told me the blast radius is bigger than I estimated" — the cascading failures were the second signal, not the first.

**39. "Five more minutes" vs. "stop and change the plan."**
Framework to describe: if an attempted fix *reduces* the error surface (fewer failures, more specific error) you're probably close — keep going. If a fix *increases* the error surface (a targeted change to one module now breaks two unrelated modules) that's evidence your mental model of the problem's boundary is wrong, not evidence you need to try harder in the same direction — that's the moment to revert to last-known-good and reconsider, which is literally what happened with the Kotlin bump in this project.

**40. Discovering someone else's uncommitted, half-finished change mid-task.**
Situation: found an uncommitted `AndroidManifest.xml` edit already in the working tree (AdMob meta-data added, but missing the `tools:replace` needed to make it build) before touching anything. Task: decide how to treat in-progress work that isn't yours. Action: didn't discard it or treat it as broken/unwanted — read it as clearly-intentional-but-unfinished, and finished it correctly (added the missing manifest attribute) rather than reverting it, since discarding someone's in-progress work without asking is the riskier default. Only later, once explicitly told to remove AdMob, was that same code removed — as an explicit instruction, not an assumption. The generalizable point: unfamiliar in-progress state defaults to "investigate and preserve," not "clean up," unless told otherwise.

**41. Preparing real store-submission assets end to end.**
What actually took the most effort: not the graphics (icon/feature-graphic generation was fast and mechanical once brand colors were known) but getting *real, working screenshots* — which required an actually-buildable app, which is what surfaced the AdMob/Kotlin build breakage in the first place. So "generate marketing images" turned into "fix a broken native build" as a hard prerequisite — a good example of how a seemingly content/design task can have a real engineering dependency hiding underneath. What was surprising going in vs. out: Play Store needs more *policy* content than expected beyond images/copy — a Data Safety questionnaire that has to accurately reflect what SDKs actually collect data (which changed the moment AdMob was removed, requiring the checklist doc itself to be updated to stay accurate), plus a privacy policy that has to be hosted at a live URL, not just written.

## 6. "Hand you the keyboard" exercises — approach notes

- **Duo/Team mode**: add `teamId: string | null` to `RoleAssignment`. In `assignRoles`, after determining which players get `'undercover'`, assign them a shared team id (e.g. `crypto.randomUUID()` or a simple incrementing id) instead of leaving it `null`; civilians/Mr. White keep `teamId: null`. New `undercoverVariants` entry: `{ id: 'duo', mrWhiteEnabled: false, undercoverCount: () => 2 }` (or scale with player count) — the interesting design question to raise out loud is *where teammates learn who their partner is* (a new reveal-screen affordance, not a `TurnEngine` change, since it's purely presentational information derived from `roleAssignments`).
